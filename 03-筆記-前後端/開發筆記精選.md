# 開發筆記精選

> 蒸餾自 cloud_drive/local-docs/note.md（2026-06-25 ~ 07-05 逐日開發筆記）的可重用結論，並補入 W4 的 temperature 結論。逐日完整脈絡見 [W2](../01-日誌/W2-0623~0629.md)～[W4](../01-日誌/W4-0707~0713.md) 日誌。

## 1. 結構化輸出（json_schema）的完整傳遞鏈

- planner 要 LLM 回固定 JSON。三種模式實測（Gemini）：純文字→回自然語言解析失敗；`json_object`→是 JSON 但欄位名錯；**只有 `json_schema` 完全正確**。結論：跨模型要可靠的結構化輸出，必須用 schema 級約束，prompt 懇求不算數。
- **傳遞鏈每一層都要轉發**：planner → ModelRouter → 各 LLM client。W2 只修外部路徑，router 本機路徑漏傳 `response_format`，直到防護測試（斷言每次呼叫必帶 schema）先紅才抓出來。
- **信封形狀不匹配要拆殼**：上游流通 OpenAI 信封形 `{"type":"json_schema","json_schema":{...}}`，Ollama 的 `format` 參數只認裸 JSON Schema——原封傳遞不可行，`_to_ollama_format()` 取出裸 schema。
- schema **不加 strict**：strict 與開放的 arguments 物件衝突，OpenAI 相容端點會拒收。
- 手寫 schema 不換 `model_json_schema()`：Pydantic 欄位都有預設值，自動產生的 schema 會沒有 required、約束更弱；改用 drift test 防手寫 schema 與 model 漂移。
- schema 只保證「形狀」，擋不住語意錯誤（幻覺技能名、缺參數）——`validate_plan`＋repair loop 是不可拆的第二道防線；技能名進一步做成 enum（依當下 registry 動態組），讓亂編在文法上不可生成。

## 2. 誠實回報與授權邊界

- `plan.reply` 是 LLM **規劃時**寫的話，本質是預言；執行完把它原樣回給使用者＝把預測當報告，這是「沒做完卻說做完」的架構根因（不是模型說謊）。修法：失敗時由程式從 StepResult（確定事實）組合訊息，不經 LLM、不可能被粉飾。
- **replan 的合法性由授權來源決定**：replan＝在使用者視線外執行新計畫，只在「授權給規則」處合法——chat 快速路徑的授權是「read-only 免確認」規則，可以 replan（兩道護欄：權限不升級、只重試一次）；confirm 的授權是「那份具體清單」、rerun 的授權是「固定配方」，偷換步驟即掏空確認閘，這兩條路徑只有誠實報告。
- 「LLM 自述不能當證據」的查證面：真做了必留 DB 稽核紀錄（見 [後端概念](後端概念.md) 三表對帳）。
- 決定**不做** agentic loop（DEC-029）的理由本身可重用：權限模型依賴完整計畫先行；本機小模型跑長程 loop 易漂移；成功案例不該付 N 倍呼叫成本;留翻案條件（eval 量出 replan 回收率不足時再議）。把「不做什麼、為什麼」寫成正式決策，比假裝完整更有價值。

## 3. 失敗隔離的不變量

- executor 遇錯全域 break 會讓無關步驟全滅。隔離後的新不變量：**每步必有一筆結果**（ok／failed／skipped 三態）、skipped ⇒ 有不可用的上游依賴、ok ⇒ 依賴全 ok——以 hypothesis property 測試（200 例）鎖住。
- 依賴判斷要合併兩種來源：顯式 `depends_on` 與引數 `from_step` 引用。
- 「引用不存在的 index」是 failed 不是 skipped——非法計畫引用與上游失敗是不同的事。
- 並行明確延後（DEC-030）：所有技能共用同一 AsyncSession 不可並發是最硬前置；隔離解決正確性、並行只省延遲，價值不對稱。

## 4. temperature 依任務類型，不依「是否結構化」

- 結構化路徑統一低溫，對「格式收斂」正確、對「寫程式」錯誤——codegen 被拖進 0.2 後產碼品質 0/4（JSON 信封完好、裡面的程式碼是壞的），per-call 覆寫 0.8 恢復。
- `structured_temperature=0.2` 的正確定位：取「打破 greedy decoding repetition loop 的最小非零溫度」以求確定性，不是因為高溫會失敗（think:false 後 4 溫度全 100%）。

## 5. registry 與沙盒的分層

- registry 是 `name→skill` 字典：`list_skills()` 把名稱／描述／參數餵進 planner prompt，LLM 只「點名」，`execute()` 查表呼叫 handler。
- 自建 skill 在後端只是 DB 裡的一段程式文字；執行時由沙盒寫成暫存 .py、`python -I` 隔離子行程跑。不可信程式碼只拿原檔唯讀複本、只能寫自己的 output_dir、禁網路禁子行程；「上傳結果」由沙盒外的可信層做——功能成立靠分層，不靠放寬沙盒。
- 接進對話的安全預設：自建 skill 一律 write 級（必跳確認）、每個預設關閉需手動啟用、「對哪個檔操作」由前端勾選注入而非讓 LLM 猜。

## 6. 外部模型實測與限流（踩雷記錄）

- **「OpenAI 相容」是協定不是廠商**：OpenAI／Gemini／Ollama／Groq 多半提供 `/chat/completions`，差別只在 base_url＋model＋key——「多組具名連線」設計的基礎。
- **Gemini free tier**：每天每模型只有 20 次請求、各模型額度獨立（換模型有全新額度）；偶發 503 high demand 屬暫時性、重試即可；429 RESOURCE_EXHAUSTED＝當日額度用光，key 本身沒壞。
- **Ollama cloud**：要用 `openai_compatible` kind＋`https://ollama.com/v1`（原生 `/api/chat` 配 `/v1` base_url 會 404，且不保證 json_schema）；模型名要用 `/v1/models` 目錄內名稱；免費 key 有限流，連測多次後全模型回 401 是**限流不是設定錯**，等重置即恢復。
- 結論：外部免費額度撐不起穩定測試，要嘛付費、要嘛多備來源輪替——這是把量測重心放在本機模型的原因之一。
