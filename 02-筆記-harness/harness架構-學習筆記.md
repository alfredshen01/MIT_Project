# 學習筆記：AI 助理 Harness 架構

> 個人複習/答辯用筆記。
> 那份講「系統長怎樣」,這份講「**我學到什麼、為什麼這樣設計、容易誤解的地方**」。
> 每節格式：**是什麼 → 為什麼 → 關鍵洞察 →（常見誤解）→ 一句話記住**。

---

## 0. 核心

**機制優先於模型自覺（mechanism over model self-awareness）。**

- **是什麼**：凡是能用「程式/規則/文法」保證的,就不要靠「模型記得要做對」。
- **為什麼**：本專案用的是**本地小模型 gemma4:26b**,不夠聰明、不穩定。與其求它自律,不如把保證外包給機制。
- **關鍵洞察**：把要求從「**請模型遵守**」升級成「**使其不可違反**」。
- **一句話記住**：**模型的能力預算很稀缺,只花在真正需要智慧的地方(規劃判斷);其餘全用機制兜底。**

這條心法解釋了後面每一個設計決策——遇到問題先問:「這能用機制解嗎?能就別靠模型。」

## 1. 六元件框架（E / T / C / S / L / V）

- **是什麼**：把「語言模型 → 可靠代理系統」的包裝拆成六個通用元件：
  | 代號 | 名稱 | 白話 |
  |---|---|---|
  | **E** | Execution Loop | 主迴圈:送訊息→解析→執行→回填;也含**模型介面** |
  | **T** | Tool/Skill Registry | 有哪些技能可用(內建/自建/現場生成) |
  | **C** | Context Manager | 塞什麼進 prompt(裁切、技能清單、**對話歷史**) |
  | **S** | State Store | 存什麼(session/訊息/技能),依 user 隔離 |
  | **L** | Lifecycle Hooks | 治理層:權限、確認、沙箱、稽核、**隱私閘** |
  | **V** | Evaluation Interface | 離線評測工具(**不在請求路徑上**) |
- **關鍵洞察**：V **畫架構圖時要放旁邊**——它是從外面打 API 來評測系統的工具,不是 runtime 的一層。
- **常見誤解**：非「通用subagent」——其實 sub-agent **目前只有 codegen 一種**。
- **一句話記住**：**E 跑、T 提供能力、C 決定看到什麼、S 記住、L 把關、V 在旁邊打分。**

## 2. Workflow 執行管線（一句話怎麼變成動作）

- **是什麼**：需求解析 → **規劃(結構化輸出)** → 技能檢查 → 權限/安全 → 顯示計畫 → **確認?** → 執行 → 記錄。
- **為什麼要「確認」這關**：寫入/破壞性操作**執行前必須使用者核可**;唯讀的才自動跑(fast-path)。
- **關鍵洞察**：**規劃 ≠ 執行**。模型先產出一份「計畫(步驟清單)」,系統檢查、你確認後才真的動手。
- **一句話記住**：**模型只負責「想計畫」,真正動手前有權限閘 + 使用者的確認把關。**

## 3. 可靠性工程：三個「量化→修正→驗證」循環（學習最深的部分）

這是兩週最精華的地方。面對「本地模型會出錯」,不是瞎調,而是**資料驅動**地一輪輪修:

### DEC-031：防跳針(結構化解碼)
- **問題**：溫度釘 0 時,模型在貪婪解碼下掉進**重複迴圈**卡死。
- **修**：`num_predict` 上限(跳針時有界失敗,不吃滿 timeout)+ 結構化請求用**低而非零**溫度。

### DEC-032：防幻覺技能(schema enum)
- **問題**：模型規劃出**不存在的技能名**。
- **修**：把計畫 schema 的技能名做成 **enum**(只枚舉真實技能)→ 幻覺技能在**取樣層就不可生成**。
- **關鍵洞察**：這是「機制優先」的教科書例——不是求模型別亂編,是讓亂編**文法上不可能**。

### DEC-033：關 thinking(治本 + 快 10×)
- **問題**：DEC-031/032 後仍殘留 ~10–20% 跳針,躲在模型的**「思考」段**(grammar 管不到那裡)。
- **修**：planner 預設 `think:false`(跳過思考直接答)。
- **數據(think:false A/B)**：thinking 開 60% 通過/3-10 跳針/92s → 關掉 **100%/0 跳針/9s(快 10×)**,規劃品質無損。
- **關鍵洞察**：**思考對這顆小模型的規劃沒幫助,卻是跳針和延遲的全部來源。**

**這三輪的共通方法(要會講)**：
> **量化(真模型 sweep 量 pass-rate)→ 定位根因(A/B 對照)→ 修正 → 再驗證。** 不猜、不靠「看起來好了」。

## 4. 模型路由 + 隱私閘（本專案賣點）

- **是什麼**：使用者**每則訊息自選模型**(本機 gemma / 具名外部連線),選定即唯一執行器。
- **隱私閘永遠在**：即使手動選外部,**敏感且無法去識別化的內容仍拒送**。
- **一句話記住**：**本地優先是隱私主軸;外送前一定過隱私閘。**

## 5. 對話記憶（近兩週新增,踩過坑）

- **是什麼**：讓助理記得前幾輪對話(把歷史回放給規劃器)。
- **根因(當初的 bug)**：對話**有存進 DB、但沒回讀**給模型 → 每輪失憶。
- **關鍵設計決策(真模型定案)**：工具結果要用 **assistant 文字**承載,**不能用 `tool` 角色**——A/B 顯示 gemma4 不消化孤立 tool 訊息(0/4 幻覺 vs 文字 4/4)。
- **限制(誠實)**：滑動視窗(~6 輪)、摘要每步 200 字截斷、單 session。
- **recall 0/5 的教訓(7/09 更正)**：多輪 eval 回想案例一度 0/5。初判「摘要截斷」是**憑讀碼的假設**;正確診斷才發現真因是**模型列根目錄傳 `parent_id="root"` 使 list_items 崩潰**(記憶根本沒名字),摘要截斷只是次因。兩者皆修 → **0/5 → 5/5**。教訓:別憑讀碼預設上游成功,**印出 runtime 才是 oracle**。
- **一句話記住**：**記憶 = 把存著沒用的歷史接回規劃器;但 v1 是「最近幾輪」的滑動視窗,不是長期記憶。**

## 6. 技能生成與治理（自我撰寫技能）

- **是什麼**：缺技能時模型**現場生成**一個,但受嚴格治理:codegen → codeguard(靜態檢查)→ sandbox(隔離跑)→ 核可 → 執行 → 安裝。
- **一句話記住**：**允許模型寫程式,但「核可+沙箱+稽核」層層把關,不讓生成碼裸奔。**

## 7. 其他問題

**Q：「規劃成唯讀」是模型自己把改名做完了嗎?**
> **不是,剛好相反——它把改名整個漏掉、什麼都沒改。** 計畫裡只剩查詢步驟(search/list),沒有 rename。「自動執行」跑的是那些**無害的查詢**,不是改名。病灶是「該動手的默默漏做」。

**Q：M3/M5 測試內容**
> 給模型一句「要先查幾樣、然後做一個寫入動作」的**複合請求**(如「幫我把某項目改名,過程中可先搜尋、列檔、看詳情」),看它能不能組出**含那個寫入步驟**的完整計畫。跑一百種、算通過率。失敗典型 = **漏掉寫入那步**。

**Q：為什麼「漏掉寫入」是模型限制,不是工程缺口?**
> 因為它產出的是**合法但語意錯**的計畫(文法對、技能名真,只是漏了 rename)。grammar/enum/think 這些機制**只能約束空間或解碼,不能替模型做「選對技能」的判斷**。而且 think 開關對它沒影響(證明不是解碼殘影)。**選擇是智慧,灌不進去**——只能靠 prompt 工程或更強的模型去「推」,無法用機制「解」。

**Q：think:false A/B?**
> A/B = 只改「思考開/關」一個變數、其他全一樣的對照實驗。thinking = 模型答前的內部推理段。關掉它 → 跳針歸零、快 10×,證明那段對小模型有害無益。

**Q：eval 怎麼「自動判對錯」?(機械判定)**
> 不是叫模型打分,而是把模型回傳的**結構化 JSON** 拿去做 `==`/`in` 比對。例如「改名要確認」→ 檢查 `status == "pending_approval"`、`"rename_item" in steps`。同樣回應必得同樣結果(不像考官打分有變異)。「規劃成唯讀」就是這樣量到:期望 `pending_approval`、實得 `auto_executed`(＝計畫無寫入步驟),一個 `==` 判失敗。

**Q：代理測試 vs 嚴謹測試?**
> **代理(proxy)**:間接驗證(如改名案例只驗「計畫含 rename + 新名」,證明使用了某個 id 但未驗全部內容)。**嚴謹**:直接驗證(回想案例要求報出全部三名)。**教訓:寬鬆的代理測試會遮蔽缺陷**——改名通過遮蔽了列檔失敗,是嚴謹回想方將其暴露。

**Q：recall 0/5 的診斷閉環教我什麼?(方法論核心)**
> 憑讀碼推論「是截斷」+ **預設列檔已成功** → 誤修 → 仍 0/5;印出實際 runtime 才發現**列檔實際崩潰(parent_id="root")**。→ **憑讀碼往前推、預設上游成功,是典型之認知陷阱;真實診斷方為可信之判準。**

**「模型限制」vs「工程缺口」(最該內化的一把尺)**
> - **工程缺口**:做一次永久解決(confirm 修復、摘要格式)。→ **值得做**。
> - **模型限制**:沒機制能保證,只能「推」、報酬遞減(寫入意圖 47%)。→ **有限投入**。
> 排優先序時**先用這把尺篩「值不值得追」**。

## 8. 一頁速記

- **核心心法**:機制優先於模型自覺——凡能以文法/程式保證者,不依賴模型自律。
- **六元件**:E 執行迴圈 / T 技能登錄 / C 脈絡管理 / S 狀態儲存 / L 生命週期治理 / V 評測介面(在旁側)。
- **執行管線**:規劃 ≠ 執行;寫入操作於執行前有權限閘與使用者確認。
- **可靠性三循環**:DEC-031 防跳針 → DEC-032 防幻覺技能 → DEC-033 關 thinking(快約 10 倍);方法為「量化 → 定位根因 → 修正 → 再驗證」。
- **對話記憶**:原本有存進 DB 但未回讀 → 接回規劃器;工具結果以 assistant 文字承載(tool 角色 gemma4 不解讀);為滑動視窗,有其限制。
- **兩把判斷尺**:①機制 vs 模型自覺(設計時) ②模型限制 vs 工程缺口(排序時)。
- **eval 判定方式**:以 `==`/`in` 機械比對結構化 JSON(非考官打分);`auto_executed` 即證明計畫無寫入步驟。
- **診斷紀律**:憑讀碼即預設上游成功為典型認知陷阱;以實際 runtime 之輸出為準。
- **誠實界線**:sub-agent 目前僅 codegen;執行串行、未並行;記憶為滑動視窗;寫入意圖規劃約 47%,為模型能力上限。
